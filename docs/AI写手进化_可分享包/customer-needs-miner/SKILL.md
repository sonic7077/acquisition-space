# 客户需求挖掘

## 输入和用途

| 输入 | 可以支持的判断 |
| --- | --- |
| 当前作品已选择的评论 | 看观众追问、反对和共鸣，补原作品没讲清的问题。高赞有助于找表达和争议，点赞数不能代表需求次数。 |
| 已关联到目标 IP 的需求快照 | 为目标人群确定选题、资料名和内容落点。保留需求 ID、原话及其来源。 |
| 用户有权限提供的聊天摘录、咨询通话文字 | 提取客户的疑问、顾虑、请求和所处阶段。保留必要原话，去掉姓名、联系方式等无关信息。 |
| 当前任务提供的已核验、未过期的共享知识 | 核对案例、身份、资质、价格、产品范围和政策等事实，保留知识 ID、日期及适用条件。 |

只分析本次可见的材料。当前作品下的对标评论提供市场观察，归入目标 IP 的需求须有明确关联。客户原话用来说明「有人这么问」，涉及事实时查证后再写。缺少需求或某类来源时，列明缺口。

## 处理步骤

1. **清洗。** 去掉广告、刷屏、表情和无关互动。按来源 ID 去重，同一条记录反复导入仍只计一次。有几条发言和有几位可辨识客户分别统计，身份不明时注明人数未知。同一客户多次追问可说明问题持续存在。
2. **分两列标注。** 内容类型按「追问 / 反对 / 共鸣 / 需求 / 待核实」，客户意向按实际言辞标注。对系统已有记录保留人工覆盖的标签；如看见疑义，说明理由供人工复核。
3. **按同一问题聚类。** 记录原话、人群、场景、发生阶段和证据编号。区分咨询前、比价时、成交后，保留会改变解法的条件。聚类名称用客户能理解的短句。
4. **按有效需求排序。** 系统口径只统计「问价格、问方案、要资料」，权重为 3、3、2。反对、共鸣单列为表达或质疑研究；「有意向」或「待核实」本身不进入有效数。只在数据足以支持时汇报次数、人数和排序，清楚标明样本范围。用户另行提供的聊天或通话作为补充观察，除非已经在系统需求快照中明确归集。
5. **落到内容动作。** 对追问直接回答，对反对先准确复述顾虑，对共鸣提炼表达，对明确需求拆出解决步骤。选题写清谁在什么情境遇到什么问题；资料名要说明读者会拿到什么；产品建议须回到已核验服务范围，缺证据的列为待验证假设。

## 输出

用一份 Markdown 需求分析报告，按以下顺序写：

1. **有效需求表**：需求主题、人群及场景、脱敏原话、内容类型、意向、有效次数、证据编号。标明哪些来自当前作品，哪些来自目标 IP 需求或用户补充材料。
2. **质疑与共鸣**：各留代表性原话及可用于改进表达的提示。
3. **优先选题与资料**：每项写明对应需求、内容切入点与可交付资料，数量按证据而定。
4. **产品观察与待核清单**：分开记录客户期待、现有服务条件和需要确认的问题。

沿用任务中可见的证据编号。数据不足时保留空缺，避免编造原话、客户数或效果。报告供人工确认和登记，输出时不写入需求库、联系客户或修改知识资料。
